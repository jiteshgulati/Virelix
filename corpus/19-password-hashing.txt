Title: Password Hashing and Storage
Author: Virelix Editorial
Category: Security
Tags: passwords, hashing, scrypt
Date: 2024-05-17
Source: Virelix sample corpus
---
Applications must never store passwords in plain text. If the database leaks, every account would be compromised immediately, and because people reuse passwords, accounts on other services would be exposed too.

The correct approach is to store a one-way hash produced by a slow, salted password hashing function. A salt is a random value generated separately for each password and stored alongside the hash. Salting ensures that two users with the same password have different hashes and defeats precomputed rainbow tables.

General-purpose hash functions such as SHA-256 are designed to be fast, which is the opposite of what password storage needs. Attackers with graphics processors can compute billions of SHA-256 hashes per second. Password hashing functions are deliberately expensive. PBKDF2 repeats a hash many thousands of times. bcrypt is based on the Blowfish cipher with an adjustable cost. scrypt and Argon2 are memory-hard, requiring large amounts of memory that make parallel hardware attacks costly.

Verification recomputes the hash from the submitted password and the stored salt and compares the result using a constant-time comparison, which prevents timing attacks from revealing how many bytes matched.

Hashing is only one layer. Systems should enforce reasonable password length, limit login attempts to slow online guessing, avoid revealing whether an email address is registered through error messages and invalidate sessions after a password reset.
